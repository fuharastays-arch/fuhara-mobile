Migration 018 is reported applied by the prior rollout; this task makes no database/schema changes. Before displaying large bigint values, validate safe integer bounds or adopt a decimal-string transport contract. PropertySummary and BookingSummary are future display projections only, unused by live queries in Phase 1.

## Identity and authority

`auth.users.id → profiles.id → user_accounts.user_id / host_profiles.user_id`.
`properties.host_id → profiles.id`; `bookings.guest_id → profiles.id`, `bookings.property_id → properties.id`.

Guests and hosts share Supabase Auth. Being a host is an account capability, not an Auth metadata role. Staff membership remains separate. The app never reads or writes staff_profiles, grants permissions, or uses service-role credentials. Server code verifies users with getUser and rereads account state. RLS is still the database enforcement layer.

Profile setup deliberately uses two recoverable operations under existing RLS: save personal profile, then create initial account if absent. If the second step fails, the UI asks the user to save again. Duplicate account inserts from concurrent requests do not overwrite status. No upsert may reset a suspended/disabled account or host flag.

## Fields explicitly not assumed

No slug, gallery, amenities, property ratings, review counts, availability calendar, favourite status, neighbourhood coordinates, cancellation policy, cleaning fee, host bio, application draft or booking payment field is invented. Destination cards are inspiration using existing brand photos, not property inventory or location photography claims. New requirements belong in MIGRATION-PROPOSALS.md.
